From N × A*
to Shared Navigation

Scaling Group Movement in Protocol Exodus

Moving one unit through a map is a pathfinding problem. Moving fifty units through the same map is not simply the same problem fifty times.

During the development of Protocol Exodus, the navigation system progressively grew from classical per-unit A* into a larger stack involving destination allocation, path following, local steering, static obstacle clearance, unit depenetration, formation topology, and tactical position reservation.

Each subsystem solved a real problem. Together, however, they exposed a more fundamental scalability issue: a group of units executing the same command was still asking the global pathfinder essentially the same expensive question once per unit. The final system uses Flow Fields for large groups while retaining individual A* where it remains cheaper. The architecture separates problems that are easy to conflate.

Global navigation decides where the group should travel. Local movement decides how individual units move through nearby traffic. Formation policy decides where each unit ultimately belongs.
Source. The implementation discussed here is developed in the SharedNavigation_exp branch of Protocol Exodus.

1. The Navigation Stack

Before discussing Flow Fields, it is useful to establish what navigation means inside an RTS. A pathfinding algorithm alone does not move a unit.

By this stage of Protocol Exodus, a Move command passed through several cooperating systems:

This is an ownership and data-flow diagram rather than a literal call stack. The important architectural change is that the expensive navigation solution can be group-owned while movement remains unit-owned.

1.1 Global Path, Local Motion

The global navigation layer produces a preferred direction. Local Steering is allowed to modify that direction, but it should not replace the global navigation decision entirely. 

Vector3 pathDirection = preferredVelocity.normalized;
Vector3 separation = CalculateSeparation(pathDirection);

Vector3 desiredDirection = pathDirection + separation * separationWeight;

Vector3 limitedDirection =
    Vector3.RotateTowards(
            pathDirection,
            desiredDirection,
            maxSteeringAngle * Mathf.Deg2Rad,
            0f);

The path remains authoritative. Steering only bends it. If a nearby unit produces an avoidance vector \(\mathbf a\), I remove the component parallel to the navigation direction \(\mathbf d\):

\[ \mathbf a_{\perp} = \mathbf a- \operatorname{proj}_{\mathbf d}(\mathbf a) \]

For normalized \(\mathbf d\):

\[ \boxed{ \mathbf a_{\perp} = \mathbf a- (\mathbf a\cdot\mathbf d)\mathbf d } \]

The separation distance depends on both navigation radii:

\[ D_{\text{sep}}=r_A+r_B+p \]

and the force increases as units approach:

\[ S(d)=1-\frac{d}{D_{\text{sep}}}. \]

1.2 Depenetration Is a Different Problem

Steering is preventative. Depenetration is corrective.

If two units still overlap because of dense traffic, numerical error, or conflicting movement, a small positional solver separates them after movement. This is intentionally not a full physics simulation; a few bounded correction passes are enough for this movement layer.

  • Steering tries to prevent overlap.
  • Depenetration resolves overlap.
  • Neither decides the global route.

As unit counts increased, local neighborhood queries were also moved toward spatial buckets rather than brute-force all-pairs checks.

Do expensive spatial work once, then make repeated queries cheap.

2. The Scaling Problem: \(N\) Units, \(N\) x A*

The original architecture was straightforward. A group Move command produced one destination per unit, then each unit requested its own A* path.

\[ U\text{ units} \rightarrow U\text{ destinations} \rightarrow U\text{ A* searches} \]

Let \(V\) be grid cells, \(E\) graph edges, and \(U\) moving units.

With a binary heap, the usual graph-search bound is:

\[ O((V+E)\log V). \]

A regular grid has bounded connectivity, so \(E=O(V)\), giving the practical simplification:

\[ O(V\log V). \]

Running this independently for an entire group gives:

\[ \boxed{ T_{\text{group}}=O(UV\log V) } \]

The critical point was not that A* was necessarily slow. The architecture was asking it to run too many times.

2.1 Dynamic Occupancy Made It Worse

Earlier iterations experimented with traversal reservations. A unit could claim its next grid cell, release its previous cell after advancing, wait when the next cell belonged to another unit, and potentially request a new path when movement could not continue.

\[ \text{conflict} \rightarrow \text{wait} \rightarrow \text{replan} \rightarrow A^* \]

That policy was gradually relaxed. Dynamic traffic became primarily a local movement problem, while strict reservations remained most useful at the final destination.

2.2 The Profiler Changed the Question

The pathfinder already used a min-heap and radius-aware traversal. But a 25-unit Move still meant roughly 25 synchronous global searches; a 50-unit Move meant roughly 50.

\[ T(U)\propto U. \]

The useful question changed from:

How can I make A* faster?

to:

Why are units executing the same order solving global navigation independently?

That question led to MovementGroup.

3. First Attempt: One A* Path, Many Units

The first Shared Navigation experiment did not begin with Flow Fields. It made the smallest possible architectural change: build one A* route for the group and let every unit consume it.

A MovementGroup owns a GroupNavigator, which exposes an abstract navigation solution: 

public interface INavigationSolution
{
    bool IsValid { get; }
    Vector3 Destination { get; }
    float NavigationRadius { get; }

    IReadOnlyList<Vector3> DebugPath { get; }

    NavigationSample SampleDirection(
        Vector3 worldPosition,
        int previousRouteSegmentIndex = -1);
}

This interface became more durable than either backend. A unit no longer needs to own a complete path. It needs a useful navigation sample from its current position:

\[ \boxed{\mathbf d=\text{SampleDirection}(P)} \]

3.1 Projecting onto a Shared Polyline

Suppose the shared route contains a segment from \(A\) to \(B\), and a unit is currently at \(P\). Define \(\mathbf s=B-A\). The projection parameter is:

\[ t= \frac{(P-A)\cdot\mathbf s} {\|\mathbf s\|^2}. \]

Since this is a finite segment:

\[ t=\operatorname{clamp}(t,0,1). \]

The closest point becomes:

\[ \boxed{P_{\text{proj}}=A+t(B-A)} \] 
float t = Vector3.Dot(current - start, segment) / segmentLengthSqr;
t = Mathf.Clamp01(t);
Vector3 point = start + segment * t;

A lightweight segment cursor avoids scanning the whole route every frame. The current sampler performs a bounded initial attachment search and a smaller forward search around the previously relevant segment.

3.2 Parallel Sampling Instead of Centerline Collapse

A naive vector from each unit directly toward the look-ahead point causes units beside the route to continuously steer inward toward the centerline.

Instead, the sampler derives direction from the projected route point toward the look-ahead point:

\[ \boxed{ \mathbf d= \operatorname{normalize} \left( P_{\text{lookahead}}-P_{\text{proj}} \right) } \] 
Vector3 lookAheadPoint = CalculateLookAheadPoint(projection);
Vector3 routeDirection = lookAheadPoint - projection.Point;
routeDirection.y = 0f;

3.3 A Polyline Is Still One-Dimensional

The limitations appeared around obstacles and larger lateral deviations. Once a unit moves away from the line, the system needs answers for corridor width, recovery distance, corner handling, static safety, look-ahead, and which section of the route remains relevant.

The shared route already solved:

\[ N\times A^*\rightarrow1\times A^*, \]

but the representation was gradually reconstructing corridor navigation around a one-dimensional centerline.

The group did not really need a shared line. It needed a useful global direction from anywhere in the navigable region.

4. Flow Fields: Making Navigation Spatial

The representation changed from:

\[ P\rightarrow\text{nearest route segment}\rightarrow\text{route tangent} \]

to simply:

\[ \boxed{P\rightarrow\mathbf d(P)} \]

A Flow Field stores navigation information over the traversable grid. Every unit in the MovementGroup samples the same field from its own world position. 

public NavigationSample SampleDirection(Vector3 worldPosition)
{
    GridCoord currentCell = field.Grid.WorldToCell(worldPosition);

    if (!field.IsInside(currentCell) || !field.IsReachable(currentCell))
    {
        return NavigationSample.Invalid;
    }

    Vector3 direction =
        SampleSmoothedDirection(
            worldPosition,
            currentCell);

    // ...
}

4.1 Radius-Aware Traversability

A narrow passage that is valid for an infantry unit may not be valid for a larger Mecha. One group-shared field therefore uses a conservative radius:

\[ \boxed{r_{\text{field}}=\max_i r_i} \]

If the largest member fits, every smaller member can safely consume the same global field.

4.2 Multi-Source Dijkstra Integration

The Flow Field begins with an integration field: the cost-to-go from every reachable cell toward the destination.

\[ C(g)=0 \qquad C(x)=\infty\;\text{ initially elsewhere}. \]

Dijkstra performs the relaxation:

\[ C(v)\leftarrow \min\left(C(v),C(u)+w(u,v)\right). \]

For the eight-connected grid, orthogonal movement uses cost \(10\) and diagonal movement uses \(14\), approximating \(\sqrt2\). Diagonal expansion also checks the adjacent orthogonal cells, preventing corner cutting.

4.3 The Destination Should Not Be One Cell

A point goal was algorithmically correct but visually poor for an RTS group: every vector eventually converged toward the same microscopic location.

A large group has an assembly region, not a point-sized destination. After an initial circular experiment, the goal was changed to a rectangular region derived from the formation half-extents.

\[ \boxed{ C(g)=0 \qquad \forall g\in G } \]

Every valid goal cell is inserted into the initial Dijkstra frontier, making the integration pass a multi-source shortest-path computation.

4.4 Clearance as a Cost, Not Only a Constraint

Binary traversability answers whether a unit can physically fit. Two legal routes are not necessarily equally desirable.

Define spare clearance:

\[ s(x)=R_{\text{clear}}(x)-r_{\text{field}}. \]

A finite discomfort penalty is:

\[ P_{\text{clear}}(x) = P_{\max} \left[ 1- \operatorname{clamp} \left( \frac{s(x)}{m},0,1 \right) \right]. \]

The relaxation becomes:

\[ \boxed{ C(v)=C(u)+w(u,v)+P_{\text{clear}}(v) } \]
Legal clearance is a hard constraint. Comfortable clearance is a soft cost.

4.5 From Integration Field to Direction Field

Once \(C(x)\) is known, each reachable cell selects the traversable neighbor with the lowest cost toward the goal:

\[ n^*=\arg\min_{n\in N(x)}\left[C(n)+w(x,n)\right]. \]

The local direction is:

\[ \boxed{ \mathbf d(x)= \frac{P(n^*)-P(x)} {\|P(n^*)-P(x)\|} } \]

4.6 Smoothing the Field

Raw grid directions change abruptly at cell boundaries. Some units exhibited high-frequency rotational jitter even with Local Steering disabled, which isolated the field sampling itself as the cause.

For local coordinates \(t_x,t_z\in[0,1]\):

\[ w_{00}=(1-t_x)(1-t_z), \quad w_{10}=t_x(1-t_z), \] \[ w_{01}=(1-t_x)t_z, \quad w_{11}=t_xt_z. \]

The blended direction becomes:

\[ \boxed{ \mathbf d(P)= \operatorname{normalize} \left( \sum_{ij}w_{ij}\mathbf d_{ij} \right) } \] 
float w00 = (1f - tx) * (1f - tz);
float w10 = tx * (1f - tz);
float w01 = (1f - tx) * tz;
float w11 = tx * tz;

Vector3 blended = Vector3.zero;
float totalWeight = 0f;

AddDirectionSample(currentCell, c00, w00, ref blended, ref totalWeight);
AddDirectionSample(currentCell, c10, w10, ref blended, ref totalWeight);
AddDirectionSample(currentCell, c01, w01, ref blended, ref totalWeight);
AddDirectionSample(currentCell, c11, w11, ref blended, ref totalWeight);

Invalid or unreachable samples are rejected, and zero vectors inside the goal region are not blended into an approaching sample from outside the goal.

5. Static Clearance, Mixed Radii and Local Movement

Flow Fields made one existing optimization even more important: StaticClearanceField.

5.1 The Expensive Version of Clearance

A radius-aware navigation system repeatedly asks:

Can a unit of radius \(r\) stand in this cell?

Searching nearby static obstacles every time is acceptable occasionally, but not when the same query appears inside A*, Flow Fields, formation allocation, attack-position allocation, and static movement safety.

5.2 Precompute Distance to Static Geometry

Instead, each grid location stores the distance to the nearest static obstruction:

\[ R_{\text{clear}}(x)= \min_{b\in B}\|x-b\|. \]

The current field is produced using a separable Euclidean distance transform on a higher-resolution lattice. Once cached, a radius-aware query becomes:

\[ \boxed{ \text{Traversable}(x,r) \iff r\le R_{\text{clear}}(x) } \]

Static buildings and terrain contribute to this field. Dynamic units do not:

\[ \text{static geometry}\neq\text{dynamic traffic}. \]

5.3 Mixed Infantry and Mecha

A representative infantry radius is approximately:

\[ r_{\text{infantry}}\approx0.45, \]

while the larger Mecha uses approximately:

\[ r_{\text{mecha}}\approx1.5. \]

The same map therefore represents different traversable spaces depending on the requesting radius. A group-shared field uses the largest member conservatively, while local separation still uses the radii of the actual pair of units.

5.4 Flow Fields Do Not Solve Avoidance

A Flow Field solves global static routing. It does not know that another unit happens to be standing half a meter to the side.

\[ \text{Flow Field sample} \rightarrow \text{preferred velocity} \rightarrow \text{Local Steering} \rightarrow \text{static safety} \rightarrow \text{movement} \]

6. Navigation Is Not Formation Policy

A Flow Field should not be responsible for preserving an exact rigid formation. Its job is to get the group through the world. Formation policy is a separate layer.

6.1 Building a Roughly Square Formation

For \(U\) units, the allocator chooses:

\[ c=\left\lceil\sqrt U\right\rceil \]

columns and:

\[ r=\left\lceil\frac{U}{c}\right\rceil \]

rows.

The spacing must account for the largest member:

\[ s_{\text{world}}\ge2r_{\max}. \]

Converted into grid cells:

\[ s_{\text{cell}}= \left\lceil \frac{2r_{\max}}{\text{cellSize}} \right\rceil. \]

Each final destination is then protected through the destination reservation system.

6.2 Why Nearest-Slot Assignment Is Not Enough

A B C
D E F
G H I

After the group deforms around an obstacle, assigning each unit to the nearest final slot can produce crossings and invert the original spatial order.

Instead, normalize the current topology around the group center:

\[ \hat P_i= \left( \frac{x_i-x_G}{e_x}, \frac{z_i-z_G}{e_z} \right), \]

and normalize the destination slot topology:

\[ \hat S_j= \left( \frac{x_j-x_F}{f_x}, \frac{z_j-z_F}{f_z} \right). \]

Then minimize the topology error:

\[ \boxed{ E(i,j)=\|\hat P_i-\hat S_j\|^2 } \]

The assignment tends to preserve left versus right, front versus rear, and the overall ordering of the group.

6.3 Final Assignment from Post-Obstacle Topology

The original assignment is computed before travel. But after moving around a building, the actual group ordering may be substantially different. Near the destination, final assignment can use the current post-obstacle topology instead.

\[ \text{initial topology} \rightarrow \text{free group travel} \rightarrow \text{post-obstacle topology} \rightarrow \text{final slots} \]

6.4 AttackPositionAllocator: Topology Applied to Combat

The same idea applies to combat deployment. A unit's angular approach direction and radial depth provide a preferred region around the target, reducing unnecessary crossing between attackers.

Candidate positions can be scored as:

\[ C= w_a C_{\text{angular}} +w_r C_{\text{radial}} +w_t C_{\text{travel}}. \]

Cheap rejection happens first:

  1. radial range,
  2. angular compatibility,
  3. cached static clearance,
  4. destination reservation only for useful candidates.

A local search radius of four cells means at most \(9\times9=81\) candidate cells per unit rather than an entire attack ring.

Do not repeatedly search a large space when topology already tells you where the useful answer probably is.

7. Making the Flow Field Actually Fast

Replacing \(N\) A* searches with one Flow Field improves the scaling model, but a badly implemented field can still be too expensive.

For a \(256\times256\) grid:

\[ 256^2=65\,536\text{ cells} \]

A field build contains several large passes:

  1. allocation / reset,
  2. traversability,
  3. Dijkstra integration,
  4. direction-field generation.

7.1 Initial Profile

Grid             256 x 256
Cells            65536
Goals            289
Expanded          ~45194

Allocation        0.82 ms
Traversability   51.75 ms
Integration     232.64 ms
Direction       150.11 ms

Total           435.54 ms

The useful information was not only the total. It was how that total was distributed.

7.2 Traversability

Reusing cached static-clearance data more directly reduced traversability from about \(51.75\) ms to around \(26\) ms: 

Traversability   26.04 ms
Integration     234.72 ms
Direction       128.51 ms
Total           390.36 ms

7.3 Dijkstra Integration

Integration was now dominant. The next pass focused on representation and queue traffic rather than changing Dijkstra itself.

A 2D coordinate can be flattened to:

\[ \boxed{i=zW+x} \]

This provides:

  • contiguous field arrays,
  • cheap settled[index] access,
  • less coordinate conversion,
  • smaller queue payloads,
  • better cache locality.

After the integration pass:

Traversability   25.82 ms
Integration     130.77 ms
Direction       128.51 ms
Total           286.07 ms

7.4 Direction-Field Indexing

Direction generation had now become as expensive as integration, which was a strong sign that the issue was data access rather than algorithmic complexity.

After making the pass more index-oriented, direction generation dropped from roughly \(128-150\) ms to around \(21-22\) ms:

8. The Payoff

The goal of Shared Navigation was not merely to make one function faster. It was to change how global-navigation cost scales with group size.

\[ N\times A^* \qquad\text{vs.}\qquad 1\times\text{shared Flow Field} \]

On the same \(256\times256\) navigation grid, representative tests produced:

Units Individual A* Shared Flow Field Improvement
35164.38 ms181.98 ms-10.7%
40194.63 ms186.47 ms4.2%
50239.66 ms184.59 ms23.0%
75463.42 ms183.92 ms60.3%
100724.96 ms193.79 ms73.3%

The first row is important: a Flow Field is not automatically faster. For 35 units, constructing a complete field over 65,536 cells is slightly more expensive than running the individual A* searches.

That is why the final architecture supports more than one navigation policy:

\[ \text{small command}\rightarrow\text{individual A*} \] \[ \text{large group}\rightarrow\text{shared Flow Field} \]

8.1 The Crossover

Individual pathfinding scales approximately as:

\[ T_{A^*}(U)\approx U\cdot T_{\text{path}}. \]

A shared field behaves differently:

\[ T_{\text{flow}}(U) \approx T_{\text{build}}(V) + U\cdot T_{\text{sample}}. \]

Each unit sample is constant-time:

\[ T_{\text{sample}}=O(1). \]

So for practical large groups, the dominant cost approaches:

\[ \boxed{ T_{\text{flow}}(U) \approx T_{\text{build}}(V) } \]

The build is not mathematically constant: it depends on map size, reachable topology, navigation radius, and goal region. The important result is that it is largely independent of how many units consume it.

The expensive navigation work now belongs to the group, not to each unit.

8.2 From Small Skirmishes to Large Groups

At this point, groups of 50, 70, or more units can consume one global navigation solution instead of producing the same number of independent paths.

Shared Navigation does not make animation, combat awareness, Local Steering, depenetration, rendering, or unit state updates free. It solves one specific scaling problem:

\[ \boxed{\text{global route computation}} \]

9. Conclusion

The navigation system in Protocol Exodus did not jump directly from A* to Flow Fields. It evolved through a sequence of increasingly specific problems:

\[ \boxed{ \begin{aligned} \text{Individual A*} &\rightarrow\text{Destination Reservations}\\ &\rightarrow\text{Local Steering}\\ &\rightarrow\text{Topology-Preserving Formation}\\ &\rightarrow\text{MovementGroup}\\ &\rightarrow\text{Shared A*}\\ &\rightarrow\text{Polyline Sampling}\\ &\rightarrow\text{Flow Fields} \end{aligned} } \]

The shared A* prototype demonstrated that a group did not need \(N\) independent global routes. But sampling a one-dimensional polyline from arbitrary positions gradually required corridor and recovery semantics.

The Flow Field changed the representation from a shared line to a spatial navigation function:

\[ \boxed{P\rightarrow\mathbf d(P)} \]

Multi-source Dijkstra supplies the global integration field. A broad rectangular goal region prevents large groups from collapsing onto a single point. Static clearance supports heterogeneous unit radii. Clearance penalties prefer comfortable routes instead of merely legal ones. Smoothed direction sampling reduces grid-boundary jitter. Local Steering handles dynamic traffic. Formation policy handles final topology and combat deployment.

Most importantly, the scaling relationship changes from approximately:

\[ \boxed{O(UV\log V)} \]

for \(U\) independent searches, toward

\[ \boxed{O(V\log V)+U\cdot O(1)} \]

for one shared field and constant-time samples.

The benchmark captures the crossover:

\[ 35\text{ units}:\qquad 164.38\text{ ms A*} \quad\text{vs.}\quad 181.98\text{ ms Flow Field} \]

but:

\[ 100\text{ units}:\qquad 724.96\text{ ms A*} \quad\text{vs.}\quad 193.79\text{ ms Flow Field}. \]

The lesson is not that Flow Fields are universally better than A*.

Navigation policy should match the scale of the command.

One unit can own a path. A hundred units moving together should probably own a navigation problem together.

Current separation of responsibilities. Navigation tells the group where to go. Steering lets units negotiate nearby traffic. Clearance tells them where they physically fit. Formation policy decides where they finally stand.

That separation is now the foundation on which the next iterations of Protocol Exodus can scale.
